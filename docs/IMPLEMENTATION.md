[原 issue](https://github.com/QiWang3569/isse-2026fall-project/issues/13) 要求硬条件、向量、精筛逐级处理。

治理流程覆盖举报、文字风险词证据、同一卖家同名商品线索、人工确认、隐藏/恢复、审计。不将举报内容本身视为事实，不自动封禁。图片审核、跨账号图片相似度、异常行为模型和完整仲裁待实现。

服务函数承担各步骤编排，权限在 API 依赖中执行，任务和操作入库；尚未引入通用 Tool Registry / Agent Orchestrator 框架。

## 首版取舍

- 阈值采用 TECH_SPEC 的 `0.82`，可通过环境变量修改。PRD 和 #13 的 `0.85` 原样保留在原始资料中。
- 商品与代蹲有效期 14 天，求购 7 天；未启用品类动态 TTL。
- 商品状态包含 `BANNED`；卖家不能重新上架已售或审核隐藏的商品。管理员恢复过期商品时仍标为过期。
- 统一分类名称，消除原文不同分类字符串无法相等匹配的问题。
- 过期状态在 API 请求时同步，查询同时检查截止时间；未实现独立清理调度器。
- 通知以 10 秒轮询获取，仅网页打开时拉取；没有后台微信或系统推送。

## 技术差异

前端 React / TypeScript / Vite；后端 FastAPI / SQLAlchemy 2.0；默认 SQLite，提供 PostgreSQL / pgvector 配置。

为开箱运行，使用同步数据库会话、请求内撮合，尚未加入 asyncpg、任务队列或独立 worker。远程向量失败时操作整体失败，不保存半完成商品。尚未验证 PRD 的并发和延迟目标。

向量与商品/意图同表，未单独建立 `item_embeddings`。用户 ID 从会话获得，不照搬原示例中客户端传 `seller_id / buyer_id` 的方式。金额以整数分保存。

会话采用随机令牌（数据库保存摘要）、HttpOnly / SameSite Cookie，并检查写请求来源。图片检查内容、大小和像素数，重编码去除元数据，绑定上传者。公开部署还需 SSO、限流、上传配额、HTTPS、备份、审计留存和版本化数据库迁移。

## 2026-09-27：买家代蹲助手

- 新增 `excluded_keywords` 与 `preferences`，与必须满足的 `keywords` 一起经用户确认后保存；相互冲突的同名条件拒绝保存。
- `AI_MODE` 与 `EMBEDDING_MODE` 独立；单聊天密钥即可运行解析和语义精筛，不必购买或接入向量接口。
- 服务编排采用固定、受约束的买家工作流：结构化解析 → 程序硬过滤 → 最多 10 件候选召回 → 模型核对 → 状态复核 → 通知。模型不拥有任意工具、数据库写入、发消息或交易权限。
- 模型精筛要求候选 ID 完整且不重复、引用逐字存在于商品文本中；必须条件缺乏证据时转为待确认，可选偏好不能作为拒绝依据。
- `match_jobs` 与业务事件同事务保存；远程精筛在无数据库会话、无写锁状态下执行，失败指数退避重试，失败后用户可手动重试，重启恢复未完成任务。
- 写入通知前复核商品和任务的状态、有效期与硬条件；模型核对期间售出、隐藏、暂停或过期的数据不会新产生通知。
- 通知展示核对依据、待确认问题，咨询草稿仅引用当前用户自己的通知问题；没有自动发送。
- 修复管理员恢复在售商品后未触发撮合的问题，并将商品状态检查放入锁内重新读取，减少并发恢复覆盖已售/隐藏状态的风险。
- 旧数据库自动进行非破坏性增量升级；没有向量回填、跨进程队列或分布式迁移功能。详细使用方式见 `BUYER_AGENT.md`。
